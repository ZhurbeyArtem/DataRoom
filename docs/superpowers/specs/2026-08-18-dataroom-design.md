# Data Room — дизайн-специфікація

Дата: 2026-08-18
Статус: затверджено, готове до планування реалізації

## 1. Мета

MVP програмного забезпечення Data Room — захищеного репозиторію документів для due diligence.
Власник створює кімнату, наповнює її папками та PDF-файлами і надає до них доступ:
або публічним посиланням, або поіменно конкретним людям. Отримувач бачить вміст лише для читання.

Пріоритети оцінювання (у порядку важливості, задані умовою задачі):

1. UX і функціональність — інтуїтивні флоу, опрацьовані граничні випадки й стани помилок
2. Дизайн і охайність — чистий вигляд, жодних нереалізованих фіч в інтерфейсі
3. Якість і читабельність коду

## 2. Стек і хостинг

| Шар | Технологія | Хостинг |
| --- | --- | --- |
| Фронтенд | React + TypeScript + Vite, TanStack Router, TanStack Query, Tailwind, shadcn/ui, Storybook | Vercel |
| Бекенд | NestJS, Prisma, Swagger, class-validator | Render |
| БД | PostgreSQL | Supabase |
| Файли | Supabase Storage (прямий аплоад браузером за signed URL) | Supabase |

Монорепо: `apps/api`, `apps/web`, npm workspaces.

### Обґрунтування ключових виборів

**Supabase як БД + Storage, але не як Auth.** Postgres і блоб-сховище в одному місці — один SDK,
signed URLs з коробки, нульова вартість. Авторизація пишеться своя: делегування Supabase Auth
перетворило б auth-модуль на тонку обгортку чужого SDK, а саме цей код має бути видно на рев'ю.

**Vite SPA, а не Next.js.** Бекенд — повноцінний NestJS. Next притягнув би другий сервер і спокусу
розмазати бізнес-логіку між ними, що читається як розмита межа відповідальності.

**Прямий аплоад у Storage.** Render у безкоштовному тарифі обмежений по пам'яті; проксіювання
файлів через API впиралося б у ліміт тіла запиту й тримало байти в пам'яті процесу. При прямому
аплоаді API не бачить байтів взагалі, а прогрес показує реальний рух даних до сховища.

## 3. Обсяг

### Входить

Обов'язкове за умовою задачі:

- Папки: створення, вкладеність, перегляд вмісту, breadcrumbs, перейменування, каскадне видалення з попередженням
- Файли: аплоад кількох PDF одночасно з drag-and-drop і прогресом на кожен файл, перегляд, перейменування з розв'язанням конфліктів, переміщення, видалення
- Шаринг: кімнати, папки або окремого файлу; публічне посилання і поіменний доступ; відкликання
- Автентифікація: email/пароль **і** Google OAuth
- Обидва застосунки задеплоєні й публічно доступні
- README з дизайн-рішеннями, ERD, розділом «How it scales» і нотаткою про використання AI

Понад обов'язкове:

- Пошук за іменем файлу по всій кімнаті (extra credit із умови)
- Кошик: м'яке видалення з відновленням
- Термін дії публічного посилання (`expiresAt`)
- Діагностичні логи в БД із TTL

### Не входить

- Історія версій файлу — модель це дозволяє додати, але UI не робимо (див. §8)
- Ролі, крім `VIEWER` — колонка `role` є з першого дня, значень поки одне
- Email-сповіщення при наданні доступу
- Автоматичні тести (unit та e2e) — це MVP, задача показати працюючий результат
- Прев'ю не-PDF форматів

## 4. Модель даних

Шість таблиць. Ключова ідея: **папка і файл — це один тип `Item`** із полем `type`,
бо майже все, що з ними робиться (перейменувати, перемістити, видалити, показати в списку,
поділитися), робиться однаково. Дві окремі таблиці розгалужували б кожну з цих операцій надвоє.

### `User`

| Колонка | Тип | Null | Опис |
| --- | --- | --- | --- |
| `id` | uuid PK | — | |
| `email` | text UK | ні | ідентифікатор користувача; нормалізується в нижній регістр на запису |
| `passwordHash` | text | так | bcrypt; null у користувачів, що зайшли лише через Google |
| `googleId` | text UK | так | |
| `name` | text | ні | |
| `avatarUrl` | text | так | |
| `createdAt` | timestamptz | ні | |

**Email нормалізується в нижній регістр при записі.** Домен за RFC 5321 і так
регістронезалежний; локальна частина формально ні, але той самий RFC радить на це не
покладатися, і жоден великий провайдер регістр не розрізняє. Причина нормалізації лежить
не в пошті, а в нашому шарингу: доступ за `USER_GRANT` перевіряється порівнянням
`granteeEmail` із email сесії. Без нормалізації власник, що вписав `Artem@Acme.com`,
надав би доступ, якого отримувач з акаунтом `artem@acme.com` ніколи не побачить — тихий
баг, невідтворюваний у розробника й незрозумілий обом сторонам. Друга причина — дублікати
акаунтів, що розрізняються лише регістром. Ціна рішення: у профілі email показується
в нижньому регістрі, а не так, як його ввели.

### `RefreshToken`

| Колонка | Тип | Null | Опис |
| --- | --- | --- | --- |
| `id` | uuid PK | — | |
| `userId` | uuid FK → User | ні | |
| `tokenHash` | text UK | ні | зберігається хеш, не сам токен |
| `expiresAt` | timestamptz | ні | |
| `revokedAt` | timestamptz | так | ротація: старий токен відкликається при видачі нового |
| `createdAt` | timestamptz | ні | |

### `DataRoom`

| Колонка | Тип | Null | Опис |
| --- | --- | --- | --- |
| `id` | uuid PK | — | |
| `name` | text | ні | |
| `ownerId` | uuid FK → User | ні | |
| `rootItemId` | uuid FK → Item | ні | коренева папка кімнати |
| `createdAt` | timestamptz | ні | |

Кімната — окрема таблиця, а не `Item` із типом `ROOT`: у неї є власник, якого немає в папки.
Якби вона була вузлом дерева, `ownerId` довелося б тримати нульованим на всіх рядках `Item`
заради кількох коренів, і кожен запит по дереву мусив би обробляти корінь як особливий випадок.
Натомість `Item` не знає про власника взагалі — власність визначається через `dataRoomId`.

### `Item`

| Колонка | Тип | Null | Опис |
| --- | --- | --- | --- |
| `id` | uuid PK | — | |
| `dataRoomId` | uuid FK → DataRoom | ні | межа орендаря; фільтрується в **кожному** запиті |
| `parentId` | uuid FK → Item | так | `null` = коренева папка кімнати |
| `path` | uuid[] | ні | id усіх предків від кореня вниз, **без себе**; для кореня `[]` |
| `depth` | int | ні | довжина `path`; дешеве сортування по рівнях і захист від надмірної вкладеності |
| `type` | enum `FOLDER \| FILE` | ні | |
| `name` | text | ні | унікальне в межах папки, регістронезалежно |
| `storageKey` | text | так | шлях у Supabase Storage; лише для `FILE` |
| `mimeType` | text | так | лише для `FILE` |
| `size` | bigint | так | байти; лише для `FILE`; `bigint`, бо `int` ламається на 2 ГБ |
| `status` | enum `PENDING \| READY` | ні | `PENDING` від видачі signed URL до підтвердження аплоаду |
| `deletedAt` | timestamptz | так | кошик; `null` = живий |
| `createdById` | uuid FK → User | ні | показується як «Власник» |
| `createdAt` | timestamptz | ні | |
| `updatedAt` | timestamptz | ні | оновлюється при перейменуванні та переміщенні |

Індекси:

- `(dataRoomId, parentId, deletedAt)` — лістинг вмісту папки, найгарячіший запит
- GIN по `path` — усе про піддерево: розмір, лічильник, каскад, перевірка доступу
- `(dataRoomId, name)` — пошук
- частковий унікальний `(parentId, lower(name)) WHERE deletedAt IS NULL AND parentId IS NOT NULL`
  — конфлікти імен усередині папки
- частковий унікальний `(dataRoomId) WHERE parentId IS NULL AND deletedAt IS NULL`
  — рівно одна коренева папка на кімнату

Часткові унікальні індекси, а не `@@unique` у Prisma, дають три речі одразу: регістронезалежність
як у Google Drive, ігнорування видаленого в кошик, і гонку двох одночасних аплоадів ловить БД,
а не перевірка `findFirst` перед вставкою.

**Чому для коренів окреме правило.** У кореневих папок `parentId` дорівнює `NULL`, і спроба
підставити замість нього фіксоване значення через `COALESCE` складає всі корені системи в одну
групу — тоді дві кімнати з однаковою назвою конфліктують навіть у різних користувачів. Для
коренів діє інший інваріант: назви кімнат можуть повторюватися скільки завгодно, а от друга
коренева папка в одній кімнаті означала б зламане дерево.

### `Share`

| Колонка | Тип | Null | Опис |
| --- | --- | --- | --- |
| `id` | uuid PK | — | |
| `itemId` | uuid FK → Item | ні | ціль: кімната (=її корінь), папка або файл |
| `type` | enum `PUBLIC_LINK \| USER_GRANT` | ні | |
| `token` | text UK | так | 32 випадкові байти в url-safe base64; лише для `PUBLIC_LINK` |
| `granteeEmail` | text | так | лише для `USER_GRANT`; нормалізований так само, як `User.email` |
| `role` | enum `VIEWER` | ні | одне значення зараз; колонка існує заради розширення |
| `expiresAt` | timestamptz | так | `null` = безстроково |
| `revokedAt` | timestamptz | так | відкликання; рядок не видаляємо, щоб лишався слід |
| `createdById` | uuid FK → User | ні | |
| `createdAt` | timestamptz | ні | |

Індекси: `(itemId)`, `(granteeEmail)`, унікальний `token`.

Один рядок `Share` — це один **спосіб доступу**, а не один користувач. Публічне посилання —
один рядок із токеном і порожнім `granteeEmail`. Доступ трьом колегам — три рядки з різними email
і порожнім токеном. Обидва режими можуть існувати на одному `Item` одночасно.

Гранти зберігаються по email, а не по `userId`. Тому запрошення людини, якої ще немає в системі,
працює само собою: вона реєструється, і при перевірці доступу її email збігається з грантом.
Ніякого окремого стану «pending invite» і жодної другої гілки коду.

CHECK-констрейнт міграцією не дає створити рядок-химеру:

```sql
CHECK (
  (type = 'PUBLIC_LINK' AND token IS NOT NULL AND grantee_email IS NULL)
  OR
  (type = 'USER_GRANT' AND token IS NULL AND grantee_email IS NOT NULL)
)
```

### `Log`

| Колонка | Тип | Null | Опис |
| --- | --- | --- | --- |
| `id` | uuid PK | — | |
| `name` | text | ні | ім'я логера |
| `level` | enum `ERROR \| WARN \| INFO` | ні | дефолт `ERROR` |
| `message` | text | ні | вміст логу — параметр `data` |
| `context` | jsonb | так | стек, url, і за потреби `userId` — заповнюється сервісом із `RequestContext` |
| `requestId` | text | так | зв'язок із конкретним запитом |
| `expiresAt` | timestamptz | ні | `now() + TTL`, дефолт 2 тижні |
| `createdAt` | timestamptz | ні | |

Індекси: `(expiresAt)` для чистки, `(name, createdAt)` для читання.

### Чому `path` як масив id

GIN-індекс по масиву робить `? = ANY(path)` індексованим пошуком. Звідси безкоштовно:

- **розмір і кількість піддерева** — один запит без рекурсії й без денормалізованих лічильників,
  які завжди розсинхронізовуються
- **breadcrumbs** — `WHERE id IN (path)`, один запит замість ходіння вгору по одному вузлу
- **каскадне видалення** — один `UPDATE ... SET deleted_at` по тому ж предикату
- **перевірка доступу** — `[item.id, ...item.path]` проти таблиці `Share`

Ціна: `move` мусить переписати `path` усього піддерева. Це один `UPDATE` із заміною префікса
масиву в межах транзакції, теж індексований. Плюс `move` перевіряє, що ціль не всередині власного
піддерева — інакше утворюється відірваний цикл.

## 5. Бекенд

### Структура

```
apps/api/src/
  common/
    prisma/          PrismaService
    crud/            BaseCrudService (create, update, delete, findOne,
                     findMany, findOneWithError, queryBuilder)
    http/            AllExceptionsFilter, TransformInterceptor,
                     ValidationPipe, RequestContext (AsyncLocalStorage)
    logger/          LogService.register()
  modules/
    auth/            dto/ interfaces/ strategies/ guards/ helpers/
    users/
    data-rooms/
    items/           dto/ interfaces/ helpers/
    shares/          + AccessService (експортується назовні)
    storage/         адаптер Supabase Storage
```

Конвенції, узгоджені з власником проєкту:

- кожен модуль має власні `dto/` та `interfaces/`
- задовгий метод ріжеться на приватні методи заради читабельності
- логіка, що повторюється в кількох сервісах одного модуля, виноситься в `helpers/`;
  імена файлів описують, що функція робить
- контролери лише передають дані в сервіси; уся логіка живе в сервісах

### Базовий CRUD

Базовий клас параметризується делегатом Prisma, а типи аргументів витягуються з нього —
тому `findMany` у нащадка знає реальні поля своєї моделі, а не `any`:

```ts
export abstract class BaseCrudService<TDelegate extends PrismaDelegate> {
  protected constructor(protected readonly model: TDelegate) {}

  create(data: …) { … }
  update(id: string, data: …) { … }
  delete(id: string) { … }
  findOne(args: …) { … }
  findMany(args?: Parameters<TDelegate['findMany']>[0]) { … }
  findOneWithError(args: …) { … }   // кидає NotFound, якщо не знайдено
  queryBuilder(query: ListQueryDto) { … }
}

@Injectable()
export class ItemsService extends BaseCrudService<Prisma.ItemDelegate> {
  constructor(prisma: PrismaService) { super(prisma.item) }
  // + власна логіка: path, конфлікти імен, каскад, переміщення
}
```

Сервіси наслідують базовий CRUD напряму, вказуючи лише свою модель.

Склад базового класу: `create`, `update`, `delete`, `findOne`, `findMany`, `findOneWithError`,
`queryBuilder`.

`findOneWithError` — той самий `findOne`, але кидає `NotFoundException` замість повернення `null`.
Це прибирає з кожного сервісу однаковий трирядковий блок перевірки й гарантує, що «не знайдено»
скрізь виглядає однаково.

`queryBuilder` перетворює query-параметри (`cursor`, `limit`, `sort`, `filter`) на аргументи Prisma.
Курсорна пагінація й сортування пишуться один раз і працюють однаково в лістингу папки, пошуку,
кошику та перегляді логів.

`delete` у базовому класі — це справжнє видалення рядка. М'яке видалення в кошик специфічне для
`Item` (треба зачепити все піддерево), тому живе власним методом в `ItemsService`, а не в базі.

### Обробка запитів

- `ValidationPipe` глобально з `whitelist: true` — зайві поля тіла відсікаються, а не проходять тихо
- `TransformInterceptor` дає єдину форму успішної відповіді
- `AllExceptionsFilter` перетворює будь-яку помилку на `{ code, message, requestId }`
  і сам пише її в `LogService` зі стеком, url і тим самим `requestId`
- `RequestContext` на `AsyncLocalStorage` носить `requestId` і `userId` наскрізь,
  щоб не протягувати їх параметром через кожен сервіс

Користувач бачить `requestId` на екрані помилки — за ним запис знаходиться в таблиці `Log`.

### Логування

```ts
register(name: string, data: string, ttl?: Duration): Promise<void>
```

Один виклик — один запис у таблиці `Log`: `name` — ім'я логу, `data` — його вміст,
`expiresAt = now() + ttl` (дефолт 2 тижні). `requestId` сервіс дістає сам із `RequestContext`,
його не треба передавати параметром. Рівень за замовчуванням — `ERROR`, бо основне призначення
таблиці саме відстеження помилок у користувачів.

Фонова задача періодично видаляє протерміноване. Запис у БД асинхронний і не блокує відповідь;
збій самого логера ніколи не валить запит.

### Доступ

Публічний глядач ходить у **ті самі** ендпоінти, що й власник — жодних дублюючих `/public/items/...`.
Запит несе або `Authorization: Bearer <jwt>`, або `X-Share-Token: <token>`.

`AccessGuard` бере `itemId` з параметрів, підвантажує `[id, ...path]` і одним запитом вирішує доступ:

```sql
SELECT 1 FROM "Share"
WHERE item_id = ANY($ancestors)
  AND revoked_at IS NULL
  AND (expires_at IS NULL OR expires_at > now())
  AND ( (type = 'PUBLIC_LINK' AND token = $tokenFromHeader)
     OR (type = 'USER_GRANT'  AND grantee_email = $myEmail) )
LIMIT 1
```

Власник кімнати проходить коротким шляхом — перевіркою `dataRoom.ownerId`.

Відмова — завжди `404`, ніколи `403`. Різниця кодів дозволила б перебором з'ясувати, які документи
існують у чужій кімнаті, а це саме та інформація, яку due diligence має приховувати.

| GET | `/items/:id/stats` | розмір і кількість елементів піддерева |
| POST | `/items/folders` | створити папку |
| PATCH | `/items/:id` | перейменувати |
| POST | `/items/:id/move` | перемістити |
| DELETE | `/items/:id` | у кошик |
| POST | `/items/:id/restore` | з кошика |
| GET | `/items/trash?dataRoomId=` | вміст кошика кімнати |
| GET | `/items/search?q=` | пошук за іменем у межах кімнати |
| POST | `/items/upload-url` | видати signed URL, створити `PENDING`-рядок |
| POST | `/items/:id/confirm` | підтвердити аплоад → `READY` |
| GET | `/items/:id/download-url` | signed URL на читання, TTL 60 с |
| GET / POST | `/items/:id/shares` | список і створення доступів |
| DELETE | `/shares/:id` | відкликати |

### Аплоад: три кроки

1. `POST /items/upload-url` — сервер перевіряє доступ до папки, розв'язує конфлікт імені,
   створює `Item` зі `status: PENDING` і повертає signed upload URL
2. браузер робить `PUT` напряму в Supabase Storage, показуючи байтовий прогрес
3. `POST /items/:id/confirm` — сервер звіряє розмір і тип із метаданими об'єкта в сховищі
   та переводить рядок у `READY`

Рядки, що лишились у `PENDING` довше години, чистить фонова задача (`@nestjs/schedule` всередині
процесу API — окремий cron-сервіс на безкоштовному Render недоступний) разом із блобами-сиротами.
Та сама задача видаляє протерміновані записи `Log`.

## 6. Фронтенд

### Структура

```
apps/web/src/
  app/            провайдери, роутер, QueryClient, тости
  routes/         файлові маршрути TanStack Router
  features/
    auth/         форми входу, guard-маршрути
    data-rooms/   список кімнат
    items/        ItemsTable, ItemRow, Breadcrumbs, діалоги
    upload/       черга аплоаду, прогрес
    sharing/      ShareDialog, публічний перегляд
    trash/  search/
  shared/
    ui/           shadcn-компоненти + Storybook
    lib/          formatBytes, cn, дати
    api/          http-клієнт + ендпоінти + типи з Swagger
```

Типи API не пишуться руками: `openapi-typescript` генерує їх зі Swagger-схеми бекенду.
Це перетворює вимогу «має бути Swagger» на реальну користь — перейменування поля в DTO
ламає збірку фронту, поки його не поправлено.

### Маршрути

| Шлях | Екран |
| --- | --- |
| `/login` · `/register` | вхід |
| `/` | список моїх кімнат |
| `/rooms/$roomId/$itemId?` | вміст папки (корінь, якщо без `itemId`) |
| `/rooms/$roomId/trash` | кошик |
| `/shared/$token/$itemId?` | публічний перегляд за посиланням |
| `/shared-with-me` | те, до чого мені надали доступ |

Публічний маршрут використовує ті самі компоненти таблиці й breadcrumbs у режимі read-only,
де дії просто приховані. Один компонент, а не два схожі.

### Шар даних

TanStack Query для серверного стану, `useInfiniteQuery` для лістингу папки (`nextCursor`
з відповіді йде в `getNextPageParam`). Ключі будуються від `['items', roomId, parentId]`,
тож інвалідація після створення, перейменування чи переміщення торкається рівно потрібних папок.

Черга аплоаду живе в Zustand, а не в TanStack Query — це транзієнтний клієнтський стан,
а не серверні дані.

### Аплоад в UI

Панель унизу праворуч: рядок на файл, реальний байтовий прогрес із `XMLHttpRequest.upload.onprogress`,
паралельність 3, кнопки «скасувати» і «повторити» на кожному рядку. Drag-and-drop на всю область
папки з підсвіткою зони.

### Перегляд PDF

Signed URL із TTL 60 секунд, рендер в `<iframe>`. Вбудований переглядач браузера дає прокрутку,
зум і друк безкоштовно; окрема бібліотека рендеру не окупається в межах бюджету.

### Storybook

Тільки `shared/ui`: кнопки, поля, діалоги, порожні стани, рядок прогресу. Story на кожен екран
з'їла б бюджет і нічого не довела.

## 7. Граничні випадки

| Ситуація | Поведінка |
| --- | --- |
| Аплоад файлу з наявним іменем | `report.pdf` → `report (1).pdf`, автоматично, без діалогу |
| Дві вкладки створюють папку з тим самим іменем | Ловить унікальний індекс БД; сервіс ретраїть із суфіксом |
| Видаляють папку, яку зараз дивиться той, кому її пошарили | Наступний запит → `404`; фронт показує «Цю папку видалено або доступ відкликано» з поверненням до доступного кореня. Рефетч при поверненні фокусу на вкладку оновлює екран сам |
| Доступ відкликано / посилання протерміноване | Той самий екран — глядач не має розрізняти ці випадки |
| Переміщення папки саму в себе або у власне піддерево | Виключено з дерева вибору в UI **і** перевірено на сервері |
| Аплоад обірвався | Рядок лишається `PENDING` і не показується в лістингу; cron чистить старші за годину; в панелі — «Помилка, повторити» |
| Видалення папки | Діалог тягне `/items/:id/stats` і пише конкретику: «Буде видалено 3 папки і 47 файлів, 128 МБ» |
| Сесія протухла під час аплоаду | Signed URL уже виданий, аплоад доїжджає; `confirm` іде після мовчазного refresh токена |
| Порожня папка / порожня кімната / нічого не знайдено | Три різні порожні стани з різним текстом і дією |
| Спроба відкрити чужий `itemId` напряму | `404`, не `403` |

## 8. Відповіді на README-питання «How it scales»

**Як обчислити сумарний розмір і кількість елементів папки разом із усім піддеревом.**
Один запит по GIN-індексу:

```sql
SELECT count(*) AS items, coalesce(sum(size), 0) AS bytes
FROM item
WHERE data_room_id = $1 AND $2 = ANY(path) AND deleted_at IS NULL
```

Без рекурсії й без денормалізованих лічильників у папках — вони потребували б оновлення на кожну
зміну в піддереві й неминуче розсинхронізовувались би. Якщо цей запит колись стане вузьким місцем,
наступний крок — кешувати результат на рівні папки з інвалідацією за `path`, не змінюючи схему.

**Що змінюється, коли в кімнаті 100 000 файлів.**
Лістинг ніколи не читає всю кімнату: він завжди обмежений однією папкою й індексом
`(data_room_id, parent_id, deleted_at)`. Пагінація курсорна, а не `offset` — `OFFSET 90000`
змусив би Postgres прочитати й відкинути 90 тисяч рядків, тоді як курсор `(name, id) > (…)`
робить index seek і читає рівно сторінку, однаково швидко на першій і на тисячній.
Курсор також не втрачає рядків, коли хтось видаляє файл під час гортання.
Пошук спирається на `(data_room_id, name)`; при потребі в пошуку за підрядком наступний крок —
триграмний GIN-індекс, знову без зміни схеми.

**Як шаринг розширюється до ролей viewer/editor без переробки моделі.**
Колонка `Share.role` існує з першого дня, просто має поки одне значення. Додавання `EDITOR` —
це міграція enum плюс декоратор `@RequireRole(EDITOR)` на мутуючих ендпоінтах: `AccessGuard`
уже повертає роль, знайдену під час розв'язання доступу. Успадкування вниз по дереву працює
так само, бо перевірка й так іде по ланцюжку `[id, ...path]`. Якщо згодом знадобляться групи
або кастомні набори прав, `role` замінюється на `permissions`, а точка перевірки лишається одна.

**Як додається версіонування файлів.** Метадані файлу (`storageKey`, `size`, `mimeType`) зараз
лежать прямо в `Item`. Версіонування додається таблицею `FileVersion(itemId, version, storageKey,
size, createdAt)` — ці три колонки переїжджають туди, а `Item` отримує `currentVersionId`.
Аплоад у конфлікт імені перестає створювати суфікс і починає створювати нову версію.

## 9. Ризики та свідомі компроміси

- **Холодний старт Render.** Безкоштовний інстанс засинає; перший запит після простою повільний.
  Пом'якшуємо пінгом за розкладом і скелетонами на фронті, які не виглядають як зависання.
- **Осиротілі блоби.** Прямий аплоад означає, що об'єкт може лягти в сховище без підтвердження.
  Фонова чистка `PENDING`-рядків старших за годину разом із їхніми блобами.
- **Переписування `path` при переміщенні великого піддерева.** Один `UPDATE` у транзакції;
  на очікуваних обсягах прийнятно. Альтернатива (closure table) складніша в підтримці
  й невиправдана для MVP.
- **Немає автоматичних тестів.** Свідоме рішення: це MVP, і завдання — показати працюючий
  результат, а не покриття. Найризикованіша логіка — розв'язання доступу; саме з неї тести
  починалися б, якби проєкт ішов далі.
- **Валідація типу файлу на клієнті.** При прямому аплоаді сервер не бачить байтів, тому
  `confirm` звіряє розмір і content-type із метаданими об'єкта в сховищі вже після завантаження.
